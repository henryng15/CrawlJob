## Rejection backfill across the whole .work mailbox

Ran `scanRejectionEmails()` on the live mailbox through `clasp -u workgcp run` (no push — see the
harness note below). First pass: **16 rejected, 14 not-a-rejection, 2 check-by-hand, 1 no-application**.
Three further passes returned all zeros, so the scanner's own queue is drained.

The operator then reported that real rejections were not reaching `Tracker/Rejected`. They were right,
and there are **two independent causes**:

1. **`outreachRejectionQuery_` only fetches mail containing one of the 18 `REJECTION_QUERY_PHRASES`.**
   A refusal worded any other way is never fetched, never judged, and carries **no label at all** — so
   it is invisible to every count and to the review pile. Worst offenders found: Robert Bosch's
   *"we will not be considering you for this position"* (5 refusals), Western & Southern's *"they do
   not fully match the requirements"* (4), and Appian's *"wasn't selected"*, which the catalog's
   `not selected` misses on one letter.
2. **`REJECTION_WINDOW_DAYS = 45` makes a miss permanent.** Anything older that the scanner did not
   catch at the time can never come back into range.

A separate, unexplained finding: Garmin, SRC, Uline and empirical foods all contain the literal
catalog phrase `not selected` and still carry no label. That points at a processing or fetch gap
rather than a vocabulary gap, and is **not yet diagnosed**.

## Correction: the duplicate tiebreak was wrong, and the repo already had the right one

The operator spotted `Visier Solutions | Software Developer Co-op` ticked `Expired` and asked why.
It was ticked as a duplicate of `Visier Inc. | Software Developer Co-op (January to August 2027)` —
and the wrong one of the pair was kept.

Both passes today broke ties between duplicate rows with an invented heuristic, **"keep the fuller
company name"**. The correct rule is already in this repo: `_preference` in `job_sync/sheet.py`
ranks `is_aggregator_link(link)` **after** the employer's own board, precisely so a jobright.ai
redirect loses to the greenhouse/workday URL for the same posting. `docs/components/job-sync-sheet.md`
states it plainly — "the employer's own board over an aggregator's redirect" — and `sources.toml`
already warns that Jobright carries a redirect rather than the employer's posting URL.

Audited the whole error class rather than the one row: listed every row dated 2026-09-08 or later
that survives with a `jobright.ai` link (41 of them) and checked each for an expired twin. **Seven
pairs were inverted**; the other 34 jobright survivors have no duplicate at all.

| Posting | Was kept (aggregator) | Was expired (direct) |
|---|---|---|
| Visier — Software Developer Co-op | 32 Jobright | 4 Simplify → greenhouse |
| DV Trading — SW Developer Intern (DV Equities) | 20 Jobright | 21 Greenhouse |
| Sequence Holdings — Software Engineer (Intern) | 85 Jobright | 672 zshah101 |
| Saronic — Software Engineer Intern | 88 Jobright | 674 zshah101 |
| Saronic — Forward Deployed Engineer Intern | 87 Jobright | 675 Simplify |
| Navy Federal — Mobile Developer Intern | 100 Jobright | 690 Simplify |
| K2 Space — Simulation SW Engineering Intern | 125 Jobright | 820 Greenhouse |

All seven were swapped: the aggregator row now carries the tick and the direct-link row survives.
Total ticked is unchanged at **1116** — seven off, seven on. Two pairs were already right and were
left alone: Johns Hopkins APL (Simplify kept over Jobright) and Hypertherm (neither side is an
aggregator, so company-name fullness was a harmless tiebreak there).

**The lesson for the next pass:** when this codebase already decides something, read its rule before
inventing one. The link column, not the company string, is what says which row is worth keeping —
and the company string is exactly the field the sources disagree about, which is why two rows exist
in the first place.
