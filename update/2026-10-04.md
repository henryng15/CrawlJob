# 2026-10-04

## The sync crawl was failing on a stale Sheets connection

- Owner asked why the crawl had been failing recently. **Seven of the nine recent sync failures
  are one bug, and it is not in the crawl.** Every source and all 1,186 ATS boards answered on the
  failing runs; the run died at its last step, writing to the sheet. Three failures on 10-01 and
  four on 10-04, all an identical `ssl.SSLEOFError` at `_already_applied`. The two on 09-29 are
  unrelated — HTTP 403 during the workspace migration, already fixed.
- **Cause.** `append_new_jobs` opens a connection, reads the Jobs tab, then runs
  `_drop_dead_rows` — a request per unsettled row, ~1,350 of them, serialised per host — and then
  reads the `App` tab on the same pooled connection. The sweep now takes seven to nine minutes, by
  which point Google's frontend has closed the idle socket. httplib2 sends on it anyway and raises.
- **Nothing retried it, which was checked rather than assumed.** httplib2 0.32.0's `_conn_request`
  catches the error as `socket.error` but only retries `ENETUNREACH`/`EADDRNOTAVAIL`;
  `googleapiclient`'s `num_retries` defaults to `0`. So one attempt, then re-raise.
- **Why now — and the first answer here was wrong, so it is written down.** The tempting story is
  that runs slowed from ~2m to ~10m. The run history says otherwise: the median sync run was
  between 7.0 and 10.2 minutes *every day* from 09-23 to 10-01 and again on 10-04, and the ~2.3m
  runs on 10-02/10-03 were the anomaly. So the exposure is weeks old and the slowness did not
  cause it — eight-to-ten-minute runs ran green through late September. Whether Google closes the
  idle socket is simply not deterministic.
- **What does hold is the direction of the correlation.** Every failing run was 9.1-10.7 minutes,
  and the two fast days did not fail once. Long runs are necessary but not sufficient, which is
  why this sat latent and then took 4 of 13 runs in one day.
- **Fix:** reconnect right after the sweep, inside `if verify_links:`. One statement. It removes
  the condition instead of depending on library retry semantics, and it covers the write and
  `_ensure_jobs_checkboxes` too. Hoisting the App read above the sweep was rejected: it would have
  handed the stale socket to `_write`, the worse place to lose it. Documented in
  [`docs/components/job-sync-sheet.md`](../docs/components/job-sync-sheet.md).
- **Not done, deliberately:** no `append_new_jobs` end-to-end test was added. There is none today,
  and a reconnect is an I/O property a fake client would assert about itself rather than about the
  socket, so it would pin the mock and not the bug. The suite stayed at 306 passed and ruff clean;
  the evidence that matters is the live long run recorded below.
- **Still open:** the 2m → 10m sweep time is untouched. Nothing is broken by it now that the run
  survives it, but if it keeps growing it will approach the 15-minute job timeout. Worth watching,
  and `PER_HOST_DELAY_SECONDS`/`WORKERS` in `liveness.py` are where it would be addressed.
